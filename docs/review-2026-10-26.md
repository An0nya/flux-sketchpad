## 1. Air-beam flash under AFS / on the pass

How the cache works (OBSERVED, js/drive-three.js:70-210): the air-beam table is a screen-sized texture (3 banks x 4 distance bins) holding, per pixel, the in-scatter integral along that pixel's eye ray out to 120 m. With cache on and cycle 8 it keeps 8 versions (slots) built with different jitter seeds and shows them in rotation by distance travelled, crossfading neighbours when cycle blend is on. A version is filled in horizontal bands over several frames (8 ms budget per frame, js/table-pace.js:5) into a spare bank, then swapped into its slot.

### F1.1 A key change keeps the old-pose slots on screen next to the new one (OBSERVED, the owner's theory is right)
- drive-three.js:165: on a key change only `tabKey`, `fillIdx`, `fill` reset. `slotValid[]` is untouched, so slots 1..7 stay valid with the OLD pose.
- drive-three.js:192-198: the shown slot is `nearestValid(phase)`. As the phase rotates it lands on new-pose slot 0 for 1/8 of the cycle and old-pose slots for the rest; cycle blend then crossfades a new slot with an old one.
- Result: the air beam alternates between the old aim and the new aim until all 8 slots are rebuilt (8 full tables at 8 ms/frame). That is the "back and forth" flash, and it lasts exactly while the strip says "building air-beam cache k/8".
- The comment at :75-76 says this is intended ("keeps the old slots shown"): it avoids a blank frame, but mixes poses.

### F1.2 Continuous steering means a fill never finishes (OBSERVED + INFERRED)
- The key quantises yaw / cornering / pitch to 0.05 deg (:108, :111). AFS swivel changes continuously in a curve, so the key changes every frame or two.
- Each key change sets `fill = null` (:165): the half-built version is abandoned and restarted at row 0. A full version needs several frames of bands, so under steady steering NO new version completes (INFERRED: depends on fill time vs. how fast yaw moves 0.05 deg).
- Result: what is shown is the pose from the last time the steering held still long enough. That is the "air beam lags the road beam". The current behaviour is a debounce (work completes only after input settles); a throttle (finish the in-flight version, then start the newest pose) gives bounded lag.
- Numbers (OBSERVED constants, drive-anim.js:661): AFS slews at AFS_RATE = pi/15 rad/s = 12 deg/s (return 30 deg/s). One 0.05 deg key step = 4 ms of swivel, so at 20 fps the key changes every frame (~12 steps per frame) while the beam swivels. Whether a version can finish in one frame depends on its fill time (the debug badge's ms/table vs the 8 ms budget); if fill > 1 frame, nothing completes until the swivel stops. In a steady curve the swivel reaches its target and holds, so the churn is at curve entry and exit.

### F1.4 Auto high beam (OBSERVED): every dip/raise is one key change, so it gets the F1.1 mixing
- A flip sets V.high and calls prepare() (drive-anim.js:1852-1853); the LUT is memoised (combineCached :1566, withHigh drive.js:140), so there is no per-frame churn. But the new LUT identity changes the key once, slot 0 refills, and slots 1..7 keep showing the OLD beam. Result: the air beam alternates between the high-beam and low-beam pictures until all 8 versions are rebuilt. That's the AHB flash.

### F1.3 On the pass, the car's grade and roll invalidate the table for nothing (OBSERVED, owner's question answered)
- tableKey's last entry is our attitude on the pass: `att ? [quant(att.pitch), quant(att.roll)]` (:114, passed at :149).
- But the table pass reads only the car-frame eye and lamps (:327-332 swap them in), the beam LUT, `pitch`/`yaw`/`cornering` uniforms, sigma, fov, size. It never reads `worldFromCar`/`carFromWorld` or anything from the attitude (OBSERVED, TABLE_MAIN in drive-three-shaders.js:349-384: ray is built in the car frame, integrated to fixed bin edges up to 120 m, no ground or terrain test).
- `p.pitch` is the suspension pitch from acceleration, only with lampPitch on (drive-anim.js:1218), not the road grade.
- History (git blame): the attitude entry came in f604787 (2026-10-22, TILT) when the table was still world-aligned. 2976aba (2026-10-23, TOUGE-AIR-RIBBON) moved the table into the car frame and left the key entry behind.
- So on the pass, every 0.05 deg change of grade or roll restarts the fill and leaves old slots showing (F1.1 + F1.2) even with AFS off. That's why the pass is worst.
- Also the pass has no cycle blend (`!p.touge` at :198; the pass programs drop the blend banks to fit 16 samplers), so slot swaps are hard cuts there.

### Fix sketch (not built)
1. Drop `att` from tableKey (one line). Expect: the pass behaves like the forest road when not steering.
2. Generations: tag each slot with the key generation it was built for; show only slots from the newest generation that has at least one finished slot; until the first new slot finishes, keep showing the old generation (no blank). One new-pose version shows at once (noisier, one jitter seed) and the other 7 fill in behind it.
3. Throttle instead of debounce: on a key change, finish the in-flight version if it is more than ~half done, else restart; always start the next fill from the newest pose. Optionally coarser quantisation for AFS yaw (the owner's beams are on a 0.25 deg grid; 0.05 deg is finer than the data).
4. Separate: the per-frame `readRenderTargetPixels` timing probe (:178) is a CPU-GPU sync every frame the table draws (see perf section).

## 2. Oncoming-traffic halo (js/drive-three-halo.js, lookup in drive-three-shaders.js:39-111)

### F2.1 The halo is NOT a cone mapped onto the beam: it is a real single-scatter march through each oncoming car's beam (OBSERVED)
- TMAIN (halo.js:50-81): for every table cell, the eye ray through that cell is marched in log steps; at each sample the oncoming lamp's intensity toward that point is looked up in THAT car's beam table (`otherIntensity(local)`, the atlas or the shared table), times the Henyey-Greenstein phase function, 1/r^2 and fog loss on both legs. Same integrand as the own air beam.
- So the halo's shape follows the beam data (cutoff, hotspot, asymmetry). What is coarse is the sampling: screen cells at 1/4 (<=4 lamps) or 1/8 of the view (:95), 6 steps per bin (24 with sub-passes near the eye), 4..32 depth bins to 120 m.
- The 10-23 handoff note ("a screen-space glow centred on the eye ... not a cone") is misleading. INFERRED reason a side view looks weak: haze scatters mostly forward (scatGFwd), so a beam seen side-on is physically much dimmer than one seen head-on. That is real, not a bug. Worth an A/B before anyone "fixes" it.
- What this does NOT cover: terrain shadowing (F2.2), each oncoming car's roll (only pitch is tilted, halo.js:137, so a car on a banked hairpin is lit as if level: INFERRED, untested), and resolution (a 1/4-1/8 screen grid plus depth bins). The hairpin breakdown the owner reports is not explained yet: need a screenshot of what "breaks" looks like.
- Culling (OBSERVED, drive.js:647-654): traffic sources are kept by distance only, not direction, so cars beside or behind still feed the table; samples behind a lamp are skipped per step. lampCone (street lamps, js/drive-three-lampcone.js) was not read in this pass.

### F2.2 No terrain shadow on the lamp-to-air leg (INFERRED, matches the 10-23 crest report)
- The integrand never tests whether the hill blocks the light between the oncoming lamp and the air sample (halo.js:70-77). Same for the own air beam (shaders.js:355-366). So air on our side of a crest, BELOW the line the beam can reach, is lit as if the hill weren't there. That inflates the glow over crests, and the veil then blows out the screen. Some pre-crest glow is real (the beam really does light the air above the crest); the part under the terrain line is not.
- Cheap variant: on the pass, the road profile is 1D along s, so a per-lamp "horizon height vs distance" test along the lamp-to-sample segment (sample the road height at 2-4 points) would cut most of it. Not designed.

### F2.3 Cost (INFERRED from counts, not measured)
- Build: per lamp near the eye, 4 sub-passes x every texel of the table. At 1920x1080 and divisor 4: 480x270 cells x 24 bins = 3.1 M texels per draw, x 6 steps = ~19 M beam lookups per draw; 4 near lamps x 4 sub-passes = 16 draws = ~300 M lookups per frame. Each lookup = asin/atan + 4 texel fetches. Polar tables are 512x64x24 = 786 k texels each, up to 2 tables x 4 sub-passes.
- Lookup: every lit fragment (ground, sky, objects, car) runs haloScatterScr = haloNu bins x 4 fetches (96 at 24 bins) + a Hermite, plus 96 texelFetch per polar table (up to 2). That's up to ~290 fetches per pixel, at full resolution x supersampling.
- That fits the owner's perf map (traffic halos = worst).
- Optimisations, in order of expected payoff:
  1. Running totals (prefix sum), approved 10-22 but NOT built (the lookup still sums every bin, shaders.js:76). A cheap pass writes cumulative C per knot; the lookup then needs the 4 knots around d only: 16 fetches instead of 96, same output up to rounding.
  2. Skip bins that cannot contain lit air for a lamp: a bin segment entirely behind the lamp (local.x <= 0 over the whole segment) or outside the beam's angular extent. Today every texel does all 6 steps and discards inside the loop.
  3. Halve the near sub-passes on phones (HALO_SUB 4 -> 2) and accept some shimmer; measure first.

## 3. Mountain pass GPU pass (js/drive-touge-three.js)

- F3.1 OBSERVED: the pass HAS terrain shadows, but only for our own lamps lighting surfaces: two 2048x1024 depth maps rendered from the lamps every frame (`shadows()`), tested in the patched lamp loop. The air-beam table, the traffic halo, and oncoming cars lighting the road have no terrain shadow (see F2.2).
- F3.2 INFERRED, correctness risk on some GPUs: the shadow test computes the surface normal with `dFdx(p)`/`dFdy(p)` INSIDE the lamp loop, after `continue`/`break` branches and inside `if(sd.x>0 && suv in range)`. Screen-space derivatives in non-uniform control flow are undefined in GLSL. Apple GPUs usually tolerate it; some mobile GPUs give garbage at pixels where neighbours took different branches (shadow-edge speckle). The surface normal `n` is already in scope in `shade()`, so using it removes both the risk and the cost.
- F3.3 OBSERVED, harmless: the shadow targets are 2048x1024 but their DepthTexture is constructed 1024x512 (:52). three.js resizes a depth texture to its target on setup (INFERRED from three's behaviour, not checked in the vendored build).
- F3.4 Cost: both shadow maps re-render every frame even when the car hasn't moved relative to the terrain (paused, or a straight constant grade). 2 extra geometry passes at 2 MP each. Cheap to skip when paused; otherwise fine.
- F3.5 OBSERVED: the ribbon mesh (191 x 11 vertices) is rebuilt on the CPU every frame with an `A.surface` call per vertex. Probably ~1 ms; not a target unless profiling says so.

## 4. Glare, veil, exposure (drive-anim.js makeGL + exposure/displayK; drive.js glareSources/veilAt/adaptStep)

- F4.1 OBSERVED, correct: the veil is the Stiles-Holladay formula, L_veil = 10 E / theta^2 (theta in degrees, clamped at 1 deg), summed over up to 32 oncoming headlamps, E = eye illuminance from each. The bloom is a separate 4-band Gaussian pyramid of the rendered HDR image (GLARE_BANDS 1/2/4/8), labelled in code as a visual approximation of the CIE 146 tail, not a fitted PSF.
- F4.2 OBSERVED, correct direction: adaptation darkens with tau 0.4 s and recovers with tau 3 s (drive.js:1037), in log2 exposure, frame-rate independent. That's the right asymmetry (fast light adaptation, slow recovery). Real recovery after a bright glare source (photostress recovery) is longer, several seconds to tens of seconds and longer with age, so 3 s is on the gentle side. A tunable, not a bug.
- F4.3 OBSERVED: the exposure target reads the veil only straight ahead (`veilAt([1,0,0], ...)`), i.e. the driver fixates the road centre. Reasonable.
- F4.4 OBSERVED, crest glare is physically derived: on the pass, each oncoming lamp's intensity toward our eye is looked up in that car's own beam table, in a frame tilted to the road grade under that car (drive-touge.js:183-191), and lamps hidden by the crest are dropped (`blocked`). So an oncoming car climbing toward a crest is pitched up at us and puts our eye above its cutoff. That's the real mechanism; the screen blowing out is the veil doing its job. What is NOT physical is F2.2 (the air glow ignores the hill).
- F4.5 Known, still true: the veil is colourless (one scalar per source). CORRECTION (same day, wave-1 agent): the flat road does tint each picked car's emit: drive-anim.js applyTrafficHeadlamps (:349-356) multiplies by the pick's tint after Headlamp.apply. I read drive.js:589 without its caller. No inconsistency.

## 5. Performance (all INFERRED from code; nothing measured this session)

Ranked by expected payoff on the phone:
1. THEORY, test before trusting: **the pass table may be almost always filling** (F1.3). Every frame of filling costs up to TABLE_BUDGET_MS = 8 ms of table work (table-pace.js:5) plus a forced CPU-GPU sync (F5.2). With the attitude in the key, that's a standing tax on the mountain pass whenever the road isn't perfectly flat. Removing `att` from the key may be the single biggest pass speedup, and it's one line. Test: watch `SD_SCATTER.recomputes` / the cache strip while cruising the pass with AFS off, before and after.
2. **Halo lookup: running totals** (F2.3.1): 96 -> 16 fetches per pixel per screen table, at full res x supersampling, in every lit shader.
3. **F5.2 Sync stalls.** `runTable` reads one texel back every frame it draws (drive-three.js:178) to time itself. A readback makes the CPU wait for the GPU to finish everything queued, so the CPU can't prepare the next frame while the GPU works. The timing feeds the band pacing, so it can't just be deleted: options are timing only every Nth frame, or EXT_disjoint_timer_query_webgl2 (already used in timeObjects) when available. Same pattern in halo `ms` but only under a test flag.
4. **Bandwidth on tile GPUs (phones):** the object target is RGBA32F with a float depth texture at w*ss x h*ss (drive-three.js:347), then blitted into another RGBA32F texture `O` (drive-anim.js:897), then composed into `hdr`. Half float would halve the traffic; `masks()` reads FLOAT but half-float targets can still be read as FLOAT in WebGL2 (INFERRED; check the exact-HDR tests before changing).
5. **Sampler budget (the "out of shader slots" wall).** WebGL guarantees 16 textures per shader. OBSERVED with `node docs/inventory/scripts/uniforms.mjs`: the worst programs are FLAT object lit+table and TOUGE object lit+table, 16 declared / 15 used. On the pass that is without the 3 cycle-blend banks; with them it would be 19 declared. Packing frees slots: the 3 table banks into one 2D array texture (`sampler2DArray`, 3 -> 1; blend banks the same, 3 -> 1), the two polar tables into one (2 -> 1). That would put cycle blend back on the pass with room to spare. `marks` is declared but unused in every object program (one slot of dead weight). Medium-size change, touches every lookup.

## 6. Terminology: code names vs standard terms (proposal, for the owner to pick)

The code coined most of these during the build. Standard names exist for nearly all of them:

| code / UI name | what it is | standard term (field) |
|---|---|---|
| air beam | own lamps' light scattered toward the eye by haze | in-scatter / single scattering (graphics); **backscatter** when it's your own beam in fog (vehicle lighting) |
| air-beam table, scatter table | per-pixel in-scatter integrals in 12 log depth slices | **froxel volume** (frustum voxels; the term Frostbite and Unreal use for exactly this) |
| beam cache, cycle 8, cycle blend | 8 pre-built jittered versions shown in rotation, crossfaded | temporal dithering (jitter rotation). NOT temporal accumulation/TAA: nothing is averaged across frames into a history buffer |
| halo, traffic halo | oncoming lamps' in-scatter, same froxel idea | in-scatter from oncoming traffic. "Halo" collides with the eye-optics halo, so it's the riskiest name |
| lamp halos (sprites) | glare veil around street lamps/signals | veiling luminance (disability glare) |
| glare veil | Stiles-Holladay veil | **disability glare, veiling luminance** (CIE) |
| glare bloom | blurred HDR pyramid | glare spread / eye point spread function (CIE 146 glare equation) |
| lamp cone | lit mist cone under a street lamp | in-scatter from street lighting (a light shaft) |
| lamp class II-V | street-lamp lateral distribution | IES lateral distribution Type I-V (IES RP-8) |
| low / high beam | | passing / driving beam (ECE R112, R48); lower / upper beam (FMVSS 108) |
| AFS | swivel with steering | Adaptive Front-lighting System (ECE R123) |
| lamp pitch | beam pitches with acceleration | dynamic beam levelling (the regulation term covers the corrective system; this models the uncorrected pitch) |
| beam, LUT | candela vs (H, V) angle grid | luminous intensity distribution, photometric table (IES LM-63 / EULUMDAT) |
| streaks, wet sheen | anisotropic specular on wet asphalt | specular reflection, anisotropic GGX BRDF |
| visibility, haze | sigma = 3.912 / V | extinction coefficient; V is Koschmieder visual range (2 % contrast threshold, ln 50 = 3.912). NOT WMO meteorological optical range, which uses 5 % (sigma = 3.0 / MOR): weather-report visibilities need converting |
